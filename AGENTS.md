## Порядок разработки

- Бери первую незавершённую задачу, зависимости которой закрыты доказательствами. Начальная задача передачи — T01.
- Один ограниченный результат за PR. Эпик сначала раздели на конкретные дочерние задачи. Не делай массовый перенос файлов вместе с исправлением поведения.
- Для дефекта сначала воспроизведи сбой соответствующим тестом, затем исправляй. Не ослабляй expected result, не выключай тест и не подменяй API заглушкой ради зелёного статуса.
- Обновляй задачу: сделано, проверено, что осталось, точный SHA, ссылки на CI, ограничения среды. Не закрывай задачу словами «основа готова».
- Если внешняя зависимость недоступна, пометь BLOCKED_EXTERNAL, назови конкретный недостающий доступ/провайдер/договор и продолжи независимую разрешённую задачу. Не выдумывай успешный production тест.
- Исправления кода готовь в ветке/PR. Публикация или merge — в пределах действующего разрешения владельца; дополнительных согласований для обычной обратимой работы не создавать. Никогда не force-push main.

## Инварианты

1. Авторизация выполняется сервером по actor → membership → workspace → store → connection/entity. Клиентские ID и выбранные модули — не права.
2. Деньги — детерминированные minor units плюс currency и источник; неизвестное и некорректное не равно нулю.
3. AI вывод — недоверенные данные. Материал, сертификаты, числа и функции требуют подтверждённых фактов. Prompt сам по себе не является контролем.
4. Free не вызывает платный API. Перед новой генерацией проверяются entitlement и атомарный бюджет; чтение истории отделено от генерации.
5. Любая внешняя запись требует общего STOP/policy gate, прав, конкретного preview/hash, актуального разрешения, идемпотентности, аудита и проверки результата. Неопределённый timeout требует сверки, а не слепого повтора.
6. Документы private, карантин до scan; доступ по tenant и business relationship. Публичные marketplace images не являются хранилищем документов.
7. AI не подтверждает физические остатки, приёмку или отгрузку. Эти факты поступают из разрешённых событий и сверяются.
8. Нельзя объявить интеграцию рабочей по наличию записи в каталоге или legacy desktop-кода.
9. Не запускать платные AI, реальные платежи, публикации WB или физические отгрузки в автоматических тестах.
10. Не добавлять Kafka/микросервисы/второй финансовый engine без измеренного обоснования. Развиваем модульное приложение.

## Проверки

Для функциональных изменений: соответствующий regression test, backend suite, frontend tests/build при изменении web/API контракта. Изменения БД и конкуренции проверяются на PostgreSQL: SQLite не доказывает блокировки и миграции. Команды и baseline — в DEVELOPER_HANDOFF.

Точные статусы Actions, Vercel и runtime проверяются отдельно. Отсутствие Actions не является success; сверяй event (push/pull_request), head_sha, conclusion и завершение. Не использовать PR-only поиск runs для заключения о push в main.

Для изменений только Markdown достаточно проверки ссылок, согласованности решений и отсутствия diff в runtime-файлах; если workflow запустился, его результат всё равно фиксируется. Изменение конфигурации CI не считается Markdown-only.

Глубокие пакетные продуктовые ревизии не заменяют проверки изменённого кода. Нельзя накопить несколько непроверенных security/write изменений ради экономии запусков.
